インターフェイスと多態性 ― クライアントクラスの書き方

Java 抽象クラスとインターフェイス／まとめプリント

この範囲で学ぶこと
  • インターフェイス Hero を使って、違うクラスを同じ呼び方で動かす（多態性）
  • クライアントクラス DoHero にオブジェクトを持たせる書き方
  • コンストラクタとsetterの違いと、それぞれのメリット

1. 全体の構造をつかもう

「ヒーローは何かしら action() できる」という約束（インターフェイス）を決め、3つのクラスがそれぞれ自分なりの中身を書きます。

«interface» Hero
void action();
▲ implements（実装する）
UltraMan
変身 → 光線
KamenRider
変身 → キック
Sailor
変身 → お仕置き
▲ Hero型として受け取る
DoHero（クライアント）
中身を知らずに action() を呼ぶだけ
ポイント：クライアント（DoHero）は相手が UltraMan なのか KamenRider なのかを知らなくてよい。
Hero 型でさえあれば action() を呼べる。これが多態性（ポリモーフィズム）です。

2. インターフェイスと実装クラス（p.77〜78）

インターフェイス

interface Hero{
    void action();   // 中身は書かない（約束だけ）
}

実装クラス（例：UltraMan）

class UltraMan implements Hero{
    String _name;
    public UltraMan(String name){
        _name = name;
    }
    public void action(){      // Hero の約束を守って action() を書く
        transForm();
        shootBeam();
    }
    public void transForm(){
        System.out.println(_name + "は変身して体が５０メートルくらいになります。");
    }
    public void shootBeam(){
        System.out.println(_name + "は腕から光線を発射します！");
    }
}

KamenRider・Sailor も同じ形です。action() の中で呼ぶメソッドだけが違います。

クラスaction() の中身
UltraMantransForm() → shootBeam()
KamenRidertransForm() → kick()
SailortransForm() → finish()

最初のクライアント（引数で受け取る版）

class DoHero{
    public void doAction(Hero h){   // 毎回、引数でヒーローを渡す
        h.action();
    }
}

// main の中
DoHero dh = new DoHero();
dh.doAction(new UltraMan("ウルトラマン"));
dh.doAction(new KamenRider("仮面ライダー"));
dh.doAction(new Sailor("セーラームーン"));
ウルトラマンは変身して体が５０メートルくらいになります。
ウルトラマンは腕から光線を発射します！
仮面ライダーは変身のときはベルトを使います。。
仮面ライダーの必殺技はライダーキックです。
セーラームーンは変身しても、あんまり変わった気がしません。
セーラームーンは月に変わってお仕置きします。

3. クライアントに「オブジェクトを持たせる」書き方（p.79）

次に DoHero を書き換えて、ヒーローをインスタンス変数に保存しておく形にします。

class DoHero{
    private Hero _hero;              // ① ヒーローをしまっておく変数

    public DoHero(Hero h){            // ② コンストラクタでセット
        _hero = h;
    }

    public void setHero(Hero h){      // ③ setter でもセットできる
        _hero = h;
    }

    public void doAction(){           // ④ 引数なし！しまったヒーローを動かす
        _hero.action();
    }
}
前（引数で受け取る） 
dh.doAction(um);
呼ぶたびに相手を渡す
後（中に持っている） 
d1.doAction();
相手は先にセット済み

4. main メソッドの書き換え（p.80）

class Test{
    public static void main(String[] args){
        // 各クラスのインスタンスを生成
        UltraMan   um = new UltraMan("ウルトラマン");
        KamenRider kr = new KamenRider("仮面ライダー");
        Sailor     s  = new Sailor("セーラームーン");

        // 作ったオブジェクトをコンストラクタに渡す
        DoHero d1 = new DoHero(um);
        DoHero d2 = new DoHero(kr);
        DoHero d3 = new DoHero(s);

        // 同じ doAction() なのに、動きはそれぞれ違う → 多態性
        d1.doAction();
        d2.doAction();
        d3.doAction();
    }
}
1
ヒーローのオブジェクトを作る
2
DoHero のコンストラクタに渡して、中にしまう
3
doAction() を呼ぶと、しまってあるヒーローの action() が動く
（実行時に「本当の型」のメソッドが選ばれる＝動的束縛）

短く書くこともできる

DoHero d1 = new DoHero(new UltraMan("ウルトラマン"));
DoHero d2 = new DoHero(new KamenRider("仮面ライダー"));
DoHero d3 = new DoHero(new Sailor("セーラームーン"));
どちらを使う？
・すっきり書きたいだけ → 短い書き方でOK
・um.shootBeam() のように doAction() 以外のメソッドも呼びたい → 変数（um など）に入れておく必要あり
→ ケースバイケースで選ぶ

5. コンストラクタと setter の違い（p.81）

今回の main ではコンストラクタしか使っていませんが、setter を用意しておくと便利な場面があります。

setter を使うと… DoHero ひとつで全員を動かせる

DoHero d = new DoHero(new UltraMan("ウルトラマン"));
d.doAction();                               // ウルトラマンが動く

d.setHero(new KamenRider("仮面ライダー"));     // 中身だけ入れ替え
d.doAction();                               // 仮面ライダーが動く

d.setHero(new Sailor("セーラームーン"));
d.doAction();                               // セーラームーンが動く
コンストラクタsetter
セットできるタイミング new するときの1回だけ 後から何度でも
メリット ・後から勝手に書き換えられない（安全）
・最初に必ず値が入るので、setter を呼び忘れても
  NullPointerException が出ない 		・中身を自由に入れ替えられる（融通が利く）
・オブジェクトを使い回せる
注意点 中身を変えたいときは新しく new が必要 セットし忘れると _hero が null のまま → エラー
まとめ：「どちらか一方が正解」ではない。
コンストラクタで初期値を必ずセットし、必要なら setter で入れ替えられるようにする ― という両方用意する形がよく使われます。

6. 確認チェック

  • インターフェイスには「メソッドの名前（約束）」だけを書き、中身は実装クラスで書く
  • Hero 型の変数には、Hero を implements したどのクラスのオブジェクトも入る
  • 同じ doAction() を呼んでも、中のオブジェクトによって動きが変わる（多態性・動的束縛）
  • コンストラクタ：生成時に1回セット／setter：後から何度でもセット
  • setter には戻り値の型 void を書くことを忘れない
