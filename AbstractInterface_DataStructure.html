「抽象クラスとインターフェイス、結局どっちを使えばいいの？」
答えのカギは “何を共通にしたいか” です。図とコードで整理しましょう。

まずは言葉の整理

教科書の言葉を、プログラムの言葉に置きかえよう

p72の文章には少し難しい言葉が出てきます。まずはクラスのどの部分のことなのかを確認しましょう。 この資料では、この 4色 で色分けして説明します。

データ構造＝ フィールド（変数） そのクラスが「どんなデータを持つか」。
private String _name;
アルゴリズム＝ メソッドの中身（処理） 「どう処理するか」。
return _name; など { } の中
アルゴリズムの形式＝ 抽象メソッド 名前・引数・戻り値だけの「約束」。中身は各クラスで書く。
void showProfile();
サプライア＝ 機能を提供する側のクラス 抽象クラスのサブクラスや、インターフェイスの実装クラスのこと。
深掘り

抽象クラス：データ構造とアルゴリズムが「受け継がれる」

抽象クラスには、インスタンス変数（データ構造）やインスタンスメソッド（アルゴリズム）を書くことができます。 それらは サブクラスにそのまま継承 されます。

データ構造 アルゴリズム アルゴリズムの形式（中身はサブクラスごと）

IPStudent も WEBStudent も、_name を持ち、getName() / setName() が使えるという点でそっくりです。 違うのは showProfile() の中身だけ。これが 「サプライア間で、データ構造は類似することになる」 の意味です。

コードabstract class / extends（p70の例）
abstract class Student {
    private String _name;        // 共通のデータ構造

    public Student(String name){
        _name = name;
    }
    public String getName(){ return _name; }        // 共通のアルゴリズム
    public void setName(String name){ _name = name; }

    public abstract void showProfile();   // 形式だけ（中身なし）
}

class IPStudent extends Student {
    public IPStudent(String name){ super(name); }
    public void showProfile(){                // 中身を書く
        System.out.println(getName() + "：IP科です。");
    }
}

class WEBStudent extends Student {
    public WEBStudent(String name){ super(name); }
    public void showProfile(){                // 中身を書く
        System.out.println(getName() + "：WEB科です。");
    }
}

class Main {
    public static void main(String[] args){
        Student[] list = { new IPStudent("山田"), new WEBStudent("佐藤") };
        for (Student s : list) {
            s.showProfile();   // 同じ呼び方で、それぞれの処理が動く
        }
    }
}
山田：IP科です。 佐藤：WEB科です。
注意： 裏を返すと、抽象クラスを継承すると 共通のデータ構造・アルゴリズムが「必ず」入ってしまいます（いらなくても外せません）。 教科書はこれを「抽象クラスの設計上の条件」と言っています。
⇒ サブクラス同士が本当に「同じデータ・同じ処理」を持つ仲間のときだけ使いましょう。
深掘り

インターフェイス：「形式」だけをそろえる

インターフェイスには、インスタンス変数もインスタンスメソッドもありません。持てるのは 抽象メソッド（形式）と public static final の定数だけです。 だから実装クラスは データ構造やアルゴリズムの影響を受けません。

学生と商品は、まったく関係のないクラスです。それでも同じ Printable を実装すれば、 「どちらも print() で表示できる」という共通の形式を持たせられます。 これが教科書の 「データ構造の異なるサプライアに共通なアルゴリズムの形式を提供する」 という意味です。

コードinterface / implements（p71の例）
interface Printable {
    void print();                  // 形式だけ（自動で public abstract）
}

class Student implements Printable {
    private String _name;        // 学生独自のデータ構造
    private String _address;
    public Student(String n, String a){ _name = n; _address = a; }

    public void print(){                // 学生用の中身
        String name = getClass().getName();   // クラス名を取得
        System.out.println(name + "\t" + _name + "\t" + _address);
    }
}

class Product implements Printable {
    private String _name;        // 商品独自のデータ構造
    private int _price;
    public Product(String n, int p){ _name = n; _price = p; }

    public void print(){                // 商品用の中身
        String name = getClass().getName();
        System.out.println(name + "\t" + _name + "\t" + _price);
    }
}

class Main {
    public static void main(String[] args){
        Printable[] items = { new Student("山田太郎", "東京都"),
                              new Product("ノートPC", 98000) };
        for (Printable p : items) {
            p.print();    // 学生も商品も「同じ呼び方」で表示できる
        }
    }
}
Student 山田太郎 東京都 Product ノートPC 98000
ポイント： Student と Product の print() は、たまたま書き方が似ていますが、これはそれぞれのクラスが自分で書いたものです。 インターフェイスから受け継いだ処理ではありません。
深掘り

もし Printable を「抽象クラス」で作ったら？

「抽象クラスでも同じことができるのでは？」と思うかもしれません。 学生と商品に共通のデータ（例えば _name と _address）を抽象クラスに持たせてみると、問題が見えてきます。

✕ 抽象クラスにした場合
問題あり
abstract class Printable {
    protected String _name;
    protected String _address; // 住所
    public abstract void print();
}
class Product extends Printable {
    private int _price;
    ...
}
  • 商品なのに 「住所」 を持たされる
  • Product は もう他のクラスを継承できない（extends は1つだけ）
○ インターフェイスにした場合
OK
interface Printable {
    void print();
}
class Product implements Printable {
    private String _name;
    private int _price;
    public void print(){ ... }
}
  • 必要なデータ だけ を自分で決められる
  • 他のクラスの継承や、別のインターフェイスの実装も同時にできる
結論： 共通のデータがない仲間同士に、共通の形式だけを持たせたいときは、インターフェイスが最適です。

「定数の一覧」だけならインターフェイス

教科書 p72 の24行目「単純に定数リストだけを作成したいような場合はインターフェイスのほうが適します」の例です。 インターフェイスのフィールドは自動的に public static final（定数）になるので、書くのが楽です。

コード定数リストのインターフェイス
interface Rank {
    int GOLD   = 3;     // 自動的に public static final
    int SILVER = 2;
    int BRONZE = 1;
}

class Main {
    public static void main(String[] args){
        int myRank = Rank.GOLD;          // 「インターフェイス名.定数名」で使える
        if (myRank == Rank.GOLD) {
            System.out.println("金メダルです！");
        }
    }
}
金メダルです！
発展：定数の一覧には enum（列挙型）もある

現在のJavaでは、決まった選択肢を表すには enum（列挙型）を使うのが一般的です。まずは「インターフェイスで定数をまとめられる」ことを押さえましょう。

コードenum を使った場合
enum Medal { GOLD, SILVER, BRONZE }

class Main {
    public static void main(String[] args){
        Medal m = Medal.GOLD;
        if (m == Medal.GOLD) {
            System.out.println("金メダルです！");
        }
    }
}

int の定数だと int myRank = 99; のようなありえない値も入ってしまいますが、enum なら決めた値（GOLD / SILVER / BRONZE）しか入りません。

まとめ：共通にできるものの違い

共通にしたいもの抽象クラスインターフェイス
データ構造（インスタンス変数）○ 書ける → サブクラスに継承される✕ 書けない（定数だけ）
アルゴリズム（処理の中身）○ 書ける → サブクラスに継承される✕ 書けない（※下の「発展」参照）
アルゴリズムの形式○ 抽象メソッドで書ける○ 抽象メソッドで書ける
定数だけの一覧△ 書けるが大げさ◎ 向いている
受け継ぎ方extends は 1つだけimplements は いくつでも
向いている関係データも処理も似ている同じ種類のクラス（学生と学生）データはバラバラだが同じ操作をしたい別の種類のクラス（学生と商品）
発展：Java 8 以降の default メソッド

この資料は基本ルールで説明していますが、Java 8 以降はインターフェイスにも default を付けると中身のあるメソッドが書けます。

コードdefault メソッド（Java 8 以降）
interface Printable {
    void print();                 // 従来どおりの抽象メソッド

    default void printTwice(){    // 中身を書ける
        print();
        print();
    }
}

ただし、インターフェイスは今でもインスタンス変数（データ構造）を持てません。共通のデータを持たせたいときは抽象クラス、という使い分けは変わりません。

📝
抽象クラスを使うときデータ構造やアルゴリズムがある程度共通で、さらに共通な形式（中身はサブクラスごとに違う）を持たせたいとき。
🔌
インターフェイスを使うときデータ構造やアルゴリズムとはあまり関係なく、共通な形式（中身はクラスごとに違う）だけを持たせたいとき。
📋
定数リストだけのときインターフェイスのほうが適している。
